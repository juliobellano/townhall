# Design: Town Hall hackathon demo, the scraper that breaks and heals

## Problem Statement

Town Hall is a cloud for small internal software (see `AGENTS.md`). Most of its five must-haves are invisible on a demo stage: nobody gets excited watching an audit log or a scale-to-zero router. The hackathon needs one story a judge remembers after 90 seconds, built by 2 people in 4 hours.

## What Makes This Cool

One protagonist, two acts. The protagonist is a single fragile scraper script.

**Act 1: a messy script becomes a safe shared tool.**
Paste an ugly script with a personal password hard-coded in it. Town Hall:
1. Explains it back in plain English and lists what it touches (sites, files, logins, schedule).
2. Moves the password out of the script into the vault.
3. Runs the original and the cleaned-up version on the same input, side by side.
4. Publishes it as a tool with a generated spec.

**Act 2: it heals.**
The target page changes (one button on a page you control). The tool fails and an alert fires. A diagnosing agent, given the error and a page snapshot but no secrets, hands its diagnosis to a separate fix-writing agent. The owner sees a "Suggested change" with a side-by-side preview of old output vs new output, approves it, and v2 goes live. v1 stays available.

Build insight: the side-by-side runner from Act 1 is the same component that shows the fix preview in Act 2. Build it once, first.

## Constraints

- 2 people, 4 hours (about 8 person-hours).
- Demo runs on a laptop. Own scripts only, throwaway box, no untrusted code from judges.
- Audience and hackathon judging criteria not yet known.

## Premises (all agreed)

1. One protagonist: a single scraper script carries both acts.
2. Laptop demo. No cloud deploy, no Caddy/HTTPS, no real SSO. The brief's "git URL to live HTTPS link" MVP is cut from the demo path.
3. Real: the Claude calls (explain-back, cleanup, diagnose, fix) and actually running both script versions. Faked: the vault (a labeled secrets file), auth, MCP depth (generate and show the spec), scale to zero.
4. The side-by-side runner is built first; both acts depend on it.
5. You control the target page, so the break is a button press. A backup screen recording exists because live demos fail.
6. Diagnoser and fix-writer are two separate Claude calls with different prompts, and no secrets reach the diagnoser. Cheap to do for real and it is one of the brief's stated decisions.

## Approaches Considered

- **A. Scripted spine (chosen).** One small web app, one hard-wired scenario, two acts. Effort M (about 8 person-hours). Risk Med: almost no slack.
- **B. Real platform (rejected for today).** Docker build, free port, Caddy HTTPS route, registry, then the acts on top. XL. Does not fit 8 person-hours and the deploy plumbing is the least memorable part. It remains the long-term path.
- **C. MCP-first, no UI (kept as a gated stretch).** Town Hall steps exposed as MCP tools and an agent drives the onboarding live. Strong on AI-native, weak on the plain-language explain-back beat that needs a visible UI.

## Recommended Approach

**A as the core build, with C as a gated stretch.**

Build the core as plain functions and let the UI call them:

```
explain(script)                  -> plain-English summary + what it touches
extract_secrets(script)          -> secrets found, placeholders inserted
cleanup(script)                  -> cleaned script (paths, secrets, inputs/outputs)
run_pair(orig, clean, input)     -> both outputs, for side-by-side
diagnose(error, page_snapshot)   -> diagnosis (NO secrets in input)
propose_fix(diagnosis, code)     -> patch + preview
apply_fix(tool, patch)           -> v2 live, v1 kept
```

**Stretch gate for C.** Wrapping these same functions as an MCP server is a thin layer. Start it only if Act 2 works end to end by T+2:45. Time-box 45 minutes, hard stop at T+3:30. If it isn't working at the stop, cut it and spend the time on rehearsal and the backup recording. The gate is written down so nobody decides it under pressure at hour 3.5.

## Open Questions

- Script language: bash + curl + grep/sed (authentic to the brief, and fragile in a realistic way) vs Python (easier for Claude to rewrite and diff). Leaning bash.
- Sandbox claim: run scripts in a Docker container, or run as a stripped-env subprocess and say so plainly. Do not label a subprocess "sandboxed" on stage.
- Demo app stack: pick the one both of you already know. Not decided.
- Who the audience is and what the judges score on. Unknown; could change the order of the two acts.
- The brief's open questions (first customer, wedge, final name, what to call an agent's proposed change) are deliberately out of scope for 4 hours. "Suggested change" is the working label in the demo.

## Success Criteria

- The full two-act story runs twice in a row on stage without touching code.
- The break is one button; the fix in Act 2 comes from a live Claude call and succeeds on at least 2 of 3 rehearsal runs. If it flakes, a cached fix is shown and labeled as such.
- A backup screen recording of a clean run exists.
- You have a one-sentence honest answer ready for "is this sandboxed?" and "can I try my own script?"
- Act 1 plus Act 2 fits in about 90 seconds of talking.

## Distribution Plan

Web app run locally from this repo with a single start command. Repo is public at github.com/juliobellano/townhall. No CI/CD for the demo. Keep the backup video next to the repo, not in it.

## The Assignment

Before anyone writes UI, build the protagonist: a local mock target page with a one-flag break, plus the ugly 30-line scraper with a hard-coded password, and run it by hand. Both acts depend on it, nothing can be rehearsed without it, and it's about 30 minutes of the 4 hours.

## What I noticed about how you think

- Your brief says "Generic customer lookup is a weak wedge (Retool and helpdesk plugins own it)." You ruled out your own safest demo before I could, which is why a plain git-URL deploy lost to the scraper story.
- Offered one demo scene, you answered "A + agent fixes a broken tool and update it to a new version." You picked the story with a beginning and an end instead of the single safe scene. That's the right instinct for a demo and it's also the scope you have to pay for.
- You said "2 person 4 hours" with no padding, then added "i think A, but also c." The appetite is bigger than the budget, the same way the brief lists five must-haves and a five-step MVP. The T+2:45 gate exists to keep that appetite from eating the demo.
