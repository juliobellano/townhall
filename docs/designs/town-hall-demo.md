## Problem Statement

Agents make custom workflows trivial to build, so people spam generated tools that are non-compliant, messy and hard to share. Town Hall is the managed place for them: an AI-native Google Drive for enterprise workflows. The demo is a recorded video for about 15 YC alum judges, built by 2 people. The demo goal in `DISCUSSION.md` is the spec; the build works backwards from it.

## What Makes This Cool

One protagonist, four beats, one pitch line: "everyone's agents can make internal tools, but my boss likes mine better."

**Protagonist:** Sarah's branch finance report, a Python script that reads 3 mock branch databases and builds the monthly report.

1. **Publish (agent).** Talk to Claude Code about the workflow; it builds the tool and deploys it to Town Hall through the Town Hall MCP. Town Hall shows the generated spec, the owner, and what the tool touches. The prompt is scripted and rehearsed; a trimmed take is fine.
2. **Use (agent).** A colleague asks their Claude for the October branch report. Claude searches Town Hall, picks the tool, asks for the missing inputs (`month`), and returns the result in chat. Contrast, five seconds: asked to read the data directly, the colleague's session is refused by demo policy (see Refusal mechanism). Through the tool it works.
3. **Use and deploy (human).** The Next.js UI: search the catalog, open a tool, fill a form generated from its spec, see the result. A thin deploy form publishes a tool.
4. **Collaborate (finale).** The colleague's agent needs a new field: a cutoff `timezone`. It calls `request_change`. The creator's agent (a Claude call inside `review_change`) reasons about it, classifies it low risk, and produces a diff. Town Hall deploys v2 and keeps v1. The colleague's agent calls `get_tool`, sees `timezone`, and uses it. One branch's October total changes. The owner has opted in to auto-deploy for low-risk changes (Decision A), so no approval click is shown; the change and diff appear on the changes page afterward.

## Protagonist spec

- **Data:** 3 SQLite files (`jakarta.db`, `taipei.db`, `london.db`), one table `transactions(id, branch, amount, created_at_utc)`. All timestamps stored in UTC.
- **v1 input schema:** `month` (string `YYYY-MM`, required), `branches` (list, optional, default all). v1 buckets by UTC month.
- **v2 adds:** `timezone` (IANA zone, optional, default `UTC`). The report buckets by month in that zone. An invalid zone returns a clear error.
- **Seeded trap:** each branch has transactions between 17:00 and 23:59 UTC on Oct 31, so a `+07:00` or `+08:00` cutoff pushes them into November. Record the expected October totals under UTC and under `Asia/Jakarta` when seeding; those numbers are the test.
- **The hand-made v2 is the target.** The creator agent's diff is validated by running it against the fixtures and comparing totals to the hand-made v2. A pre-baked copy of that diff is the retake fallback and is labeled "cached".

## Refusal mechanism and data access

- The data lives in a directory the Town Hall server process reads. The colleague's Claude Code session has a deny rule on that path and on `sqlite3` (demo policy, shown on screen as "company policy"). The tool reads the data; the agent does not.
- This is a policy layer, not OS isolation. The voiceover says so, and the tool runs as a stripped-env subprocess that is never called "sandboxed". Docker with a read-only mount is an upgrade only if it is already running.
- `get_tool` returns the schema, so "the agent gets the report, not the database" is visible on screen.

## Identity and audit

- Each MCP config sets `TOWNHALL_USER` and `TOWNHALL_AGENT`, sent on every call (the two-user stub).
- Every `run_tool` writes a row: person, agent, tool, version, inputs, output summary, time. A polished audit page is optional; the table is not.

## Constraints

- 2 people, 4 hours (about 8 person-hours). Confirmed for this wider scope (Decision C).
- The demo is a recorded video. Retakes are fine. Anything cached or scripted is labeled on screen or in the voiceover.
- Judges are about 15 YC alums. Vybe (a YC company) is a close neighbor.
- Laptop, our own scripts only, no untrusted code.

## Premises

**Agreed in the session:** one protagonist (Sarah's branch report); direct-versus-tool contrast instead of a checksum claim (xlsx files embed timestamps, so byte-identical output is not a real claim); MCP is core; video, not live; the four beats from the demo goal.

**Proposed, not yet confirmed:**
- Real: Claude Code publishing through the MCP, the Town Hall MCP, the tool running, the creator-agent call, a real diff. Faked: SSO (the two-user stub), vault, scale to zero.
- Tool contract (amended by eng review): a tool script reads JSON on stdin, writes JSON on stdout, and prints its own JSON Schema with `--schema`. The input schema comes from the code, so spec and code cannot drift. An LLM call writes only the description and the `touches` list at publish, cached and labeled. `publish_tool` rejects a script that does not follow the contract. Claude Code is told the contract in the tool description.
- The MCP is generic (`search_tools`, `get_tool`, `run_tool`, `request_change`). Schemas are read through `get_tool` at call time, so nothing re-registers when v2 ships and a client's cached tool list does not matter.
- Creator-agent output (amended by eng review): structured JSON with a decision and the full new source (a full-file replacement, not a patch). The platform computes the diff shown in the UI. Do not describe `temperature 0` as a determinism pin; the 5-run eval is the control.
- Deploy gate (amended by eng review), run by the platform before auto-deploy, and the rubric made mechanical: (1) schema diff: only optional properties with defaults may be added, nothing removed, nothing newly required; (2) source scan: imports outside an allowlist (start with `zoneinfo`, `datetime`) and network, subprocess and file-open tokens are rejected, a cheap lint and not a claimed security control; (3) fixture runs: v2 at defaults must equal v1's output, and v2 with `timezone=Asia/Jakarta` must match the recorded totals. A rejected change shows its reason on the changes page and v1 stays live. This follows AGENTS.md.
- Stack (amended by eng review): one Next.js app (TypeScript, `nodejs` runtime) serving both the UI and the MCP server at `/api/mcp` over streamable HTTP, using a Web-standard adapter (`mcp-handler` or the SDK's own, version pinned after the spike). Fallback: a second small HTTP process sharing the same lib. SQLite for the registry as a `globalThis` singleton, and a Python report script (stdlib `sqlite3`). No monorepo and no stdio MCP package.
- **UI rule (set by the team):** every UI component comes from shadcn/ui, and icons come from `lucide-react`. Do not hand-build a component if shadcn has one. Likely fits: Input, Button, Card, Table, Badge, Dialog, Tabs, Form, Select (catalog, tool form, changes page, deploy form).
- Differentiation line: "Gateways govern tools that already exist, app hosts need an app. We take the script on Sarah's laptop and make it a governed tool any agent can call."

## Data shapes (minimal)

```
tools(id, name, owner, created_at)
versions(tool_id, version, source, spec_json, created_at)        // spec = JSON Schema inputs
runs(id, tool_id, version, person, agent, inputs, output, at)
changes(id, tool_id, requester, need, decision, diff, status, from_v, to_v)
```

```
publish_tool(source, meta)           -> tool + v1; schema read from `--schema`, contract enforced
search_tools(query) / get_tool(id)   -> catalog entries, spec
run_tool(id, version?, inputs)       -> result + runs row
request_change(tool_id, need)        -> changes row, creator agent invoked
review_change(change_id)             -> decision + new full source (Claude call, structured JSON); platform computes the diff and runs the deploy gate
deploy_change(change_id)             -> v2 live, v1 kept
```

The MCP server and the Next.js UI both call these functions.

## Cross-Model Perspective

An independent Claude subagent read a summary and said:
- Steelman: the "publish" button for the long tail of agent-written scripts; value is one canonical version and data that stays put while the result travels.
- Key insight: the real competitor is a colleague typing "Claude, make me the branch report." The demo must answer that on screen.
- Challenged premise: "identical output, matching checksums". Accepted and replaced by the direct-versus-tool contrast.
- Kept from its prototype advice: no network and read-only data for the runner, an audit row per call, and show the tool's schema. Its ACL page and polished runs page were cut.

A second independent review of this doc scored an earlier draft 6.5/10 and found 19 issues. This version fixes 17 of them in one pass; the remaining two were settled by Decisions A to C and the video cap stays an open question. This version has not been re-reviewed.

## Approaches Considered

- **A+. Consume, collaborate, deploy spine (chosen).** One protagonist, MCP plus a small Next.js app over shared functions. Effort M, risk Med.
- **B. Full platform story.** Real container deploy and every must-have. Rejected: XL.
- **C. Two Claudes, no web UI.** Rejected: the demo goal needs a human interface.
- **Scraper breaks-and-heals design.** Superseded: not in the demo goal.

## Decisions

- **A. Beat 4 auto-deploys.** The owner has opted in, per AGENTS.md's allowance for an optional field with a default. The creator agent deploys; the change and diff show on the changes page afterward. No approval UI is built. A change that fails the rubric is rejected and left for the owner.
- **B. The "PR" is a change record plus diff in Town Hall,** labeled as such on screen. Not a real git PR or GitHub PR.
- **C. The budget stays at 4 hours with 2 people.**

## Engineering Review (/plan-eng-review, 2026-11-11)

**Decisions**
- Scope reduced to one Next.js process serving the UI and MCP at `/api/mcp` over HTTP. Fallback: a second small HTTP process.
- Tool contract: stdin JSON in, stdout JSON out, `--schema` prints the input schema.
- Deploy gate: schema diff, source scan (a lint), fixture runs, before any auto-deploy.
- Creator-agent reliability: a 5-run eval; film live only at 4 of 5 or better, otherwise the cached decision, labeled.
- A 20-minute spike up front for MCP-in-Next and one creator call.
- Creator output is structured JSON with a full-file replacement; the platform computes the diff.
- Kept as designed: the gate-result panel and the audit table stay only-if-ahead.
- The outside-voice notes on voiceover wording, schema extraction, refusal hardening, publish_tool messaging, schedule budgeting, the seeded trap, and the take rule were reviewed and not folded in. Unknown inputs were then added back on their own: the runner rejects any input key the tool version doesn't declare.

**Implementation notes (no decision needed)**
- Route handler declares the `nodejs` runtime; SQLite is a `globalThis` singleton so dev reloads don't open several connections.
- Every `run_tool` failure (bad inputs, non-zero exit, timeout, unknown version) returns a structured error and the MCP marks it `isError`, so the agent can read it and retry. The runner has a hard timeout and a stripped environment.
- `request_change` runs the creator agent synchronously with a 90-second cap, then falls back to the labeled cached decision.
- The schema form is a small `SchemaForm` built from shadcn `Input`, `Select`, `Checkbox`, `Label` and `Button`; shadcn has no JSON-Schema form component.
- Film against `next build && next start`, not `next dev`, so the first `/api/mcp` hit doesn't stall on camera.
- Commit each feature as soon as it is implemented and its tests pass (team rule). One feature, one commit; never commit a broken or untested feature.

**What already exists:** nothing. The repo is docs only. Reuse off the shelf: shadcn/ui, lucide-react, the MCP SDK or `mcp-handler`, `better-sqlite3`, the Anthropic SDK, a JSON-Schema validator, and Python's `zoneinfo`.

**Not in scope:** real SSO, vault, scale to zero; a real GitHub PR; Docker sandboxing; a human approval screen and security-review queue (in TODOS.md); the audit page and search ranking unless ahead; onboarding of messy scripts; multi-language tools; the scraper heal design; rollback and fork.

**Tests (greenfield, 28 planned paths, tests written with the code)**
- Vitest for `lib/`: runner (happy, invalid inputs, undeclared input keys rejected, non-zero exit, timeout, stripped env), schema read (`--schema`, missing rejected), gate (add optional ok; remove or newly required rejected; allowlist; v2 at defaults equals v1), changes (malformed creator output, reject path, accept then v2 live and v1 kept).
- Python `unittest` for the report script: UTC buckets, `Asia/Jakarta` moves the seeded Oct 31 rows, invalid zone errors, empty month returns zeros.
- One MCP-client integration test against `next build && next start`: publish, search, get, run, request change, get, run with `timezone`.
- A 5-run creator-agent eval script (pass = gate passes and totals match).
- Test plan for QA: `~/.gstack/projects/townhall/julio-main-eng-review-test-plan-20261111-200953.md`.

**Failure modes**
- Subprocess hang: timeout, structured error, visible. Covered.
- Script without `--schema`: publish rejected with a message, visible. Covered.
- Creator output malformed or API timeout: rejected with a visible reason, or the cached decision, labeled. Covered.
- Gate source scan bypassed by indirect Python: accepted risk for our own scripts; say "fixture-validated", not "safe".
- MCP session loss on dev reload: avoided by building and starting, and checked in the spike.
- Missing identity header: rejected and tested.
- A call that passes an input key the version doesn't declare (for example `timezone` against a v1-pinned call): the runner rejects undeclared keys with a clear error, regardless of the schema, so a finance report never silently ignores an input and returns a wrong total. Tested (task T9).

**Parallelization:** two lanes. A (P1): protagonist, creator-agent spike, gate, changes, eval (`python/`, `data/`, `lib/gate`, `lib/changes`). B (P2): Next.js and shadcn init, MCP spike, registry, runner, UI (`app/`, `lib/registry`, `lib/runner`). Sync at T+1:10 and T+2:00 since both lanes touch `lib/`.

## Success Criteria

- One video, from honest takes, shows all four beats within the length cap (target about 2 minutes until known).
- After the change, the colleague's next call uses `timezone` and the October total for the seeded branch matches the expected value recorded at seed time.
- The refusal on the direct data ask and the success through the tool are both on screen.
- Short, honest answers written down for: "is this sandboxed?" (no, a stripped-env process plus a policy layer), "isn't this Vybe or Retool?" (the differentiation line), "why not let Claude regenerate it?" (the data cannot leave and one canonical version).
- Every cached or scripted piece is labeled.
